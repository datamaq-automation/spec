# Directivas de Desarrollo con Aider (Frontend — Vue 3 + Vite + FSD)

Este proyecto se rige por **Spec-Driven Development (SDD)**, **Feature-Sliced Design (FSD)** y el **Guantelete de Restricciones (*Constraint Gauntlet*)**.

---

## 1. Fuente Única de la Verdad (SSOT)
* **Especificación del Sistema:** Toda regla de presentación, integración con APIs, contratos DTO y requisitos funcionales (FR) o no funcionales (NFR) están definidos en [`docs/srs-spec-frontend-vue-vite.md`](file:///home/agustin/proyectos_software/spec/docs/srs-spec-frontend-vue-vite.md).
* **Directiva:** No inventes endpoints, schemas de validación ni flujos fuera del SSOT. Si un cambio altera contratos de API o diseño de vistas, solicita confirmación antes de implementar.

---

## 2. Las 7 Reglas Innegociables de Arquitectura
1. **Regla de Dependencia de Capas (Validada por `test_architecture.mjs`):**
   * `src/shared/`: UI base y utilidades puras. Prohibido importar de `core`, `features` o `app`.
   * `src/core/`: Lógica pura, servicios, schemas Zod y tipos. Solo puede importar de `shared`.
   * `src/features/`: Módulos funcionales desacoplados. Pueden importar de `core` y `shared`. Prohibido importar de `app` o entre features directamente.
   * `src/app/`: Enrutamiento, stores globales y bootstrapping. Puede importar de todas las capas inferiores.
2. **Separación Estricta de Archivos `.ts` vs `.vue`:**
   * Archivos `.vue` (SFC): Presentación y template puro (`<script setup lang="ts">`). Prohibido colocar lógica de negocio compleja o llamadas directas a APIs en componentes.
   * Archivos `.ts`: Toda la lógica reutilizable, validación con Zod, stores Pinia, clientes HTTP (Axios) y composables. `src/core/` es 100% `.ts`.
3. **Barriles de Exportación Controlados (`index.ts`):**
   * El re-export en cascada (`export *`) solo se permite en la API pública de una feature (`src/features/{feature}/index.ts`).
   * Fuera de `features/`, los `index.ts` deben usar exports explícitos (`export { ... }`) o módulos nombrados. Prohibido `export *` generalizado.
4. **Imports 100% Absolutos con Alias `@/`:**
   * Prohibidos los imports relativos entre capas (`../`). Exige siempre el alias `@/` (`@/core/...`, `@/features/...`, `@/shared/...`).
5. **Tipado Estricto Exhaustivo (Cero `any`):**
   * Prohibido el uso de `any`, `@ts-ignore`, `@ts-nocheck` o `@ts-expect-error`. `npm run type-check` (`vue-tsc --noEmit`) debe reportar 0 errores.
6. **Vistas Delgadas (*Thin Views*):**
   * Los componentes en `views/` solo orquestan componentes y composables; delegan el estado y las operaciones asíncronas en `stores/` y `services/`.
7. **Cero Secretos y Variables de Entorno Seguras:**
   * Solo se permiten variables con prefijo `VITE_` para configuración pública (URLs de backend, flags de UI). Prohibido quemar API keys privadas, contraseñas o tokens en el código fuente.

---

## 3. Matriz de Verificación (Constraint Gauntlet)
Antes de dar cualquier tarea por completada o sugerir un commit, verifica que el código supere el 100% de la siguiente batería:

```bash
# 1. Linter
npm run lint

# 2. Chequeo de Tipos Estricto (TypeScript + SFCs)
npm run type-check

# 3. Verificación de Formato
npm run format:check

# 4. Guantelete de Restricciones Estático (Capas FSD, cero any, barriles, imports absolutos, secretos)
node scripts/test_architecture.mjs

# 5. Suite de Pruebas Unitarias
npm run test:unit
```

---

## 4. Convención de Commits
* Utiliza el estándar **Conventional Commits**:
  * `feat: <descripcion>` (nuevas funcionalidades o vistas)
  * `fix: <descripcion>` (corrección de bugs o estilos)
  * `refactor: <descripcion>` (reestructuración sin cambio visual ni funcional)
  * `test: <descripcion>` (añadir o actualizar tests unitarios o e2e)
  * `docs: <descripcion>` (actualizaciones de specs o guías)
  * `chore: <descripcion>` (mantenimiento de dependencias o configs de build)
